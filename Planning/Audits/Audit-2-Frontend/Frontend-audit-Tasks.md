## ⚙️ EXECUTION PROTOCOL (the loop algorithm — follow exactly, every iteration)

1. **Load state.** Read the STATE block, the Build Log (bottom), and this phase's task list. Read `Frontend-audit.md`'s section for the task you're about to do (each task cites it).
2. **Select task.** The next task is the **first task in document order** whose box is `[ ]` or `[~]`. Never skip ahead, except: if the selected task is `[!]` blocked or gated on a red human item, take the next `∥`-marked task instead.
3. **RESEARCH (mandatory, before writing any code).**
   - Read the **current** source of every file the task names, in full, before editing. The audit's file:line cites were verified on 2026-07-18 but the tree moves — **grep for the quoted code/strings to re-anchor every cite; if a cite is wrong, record it in the Errata table and proceed against reality.**
   - Read the spec sections the task cites (they are the authoritative behavioral detail — this ledger deliberately doesn't duplicate them).
   - Check `app/package.json` before assuming a library exists; install with `npx expo install <pkg>` (never bare npm for Expo-managed deps).
   - For any backend-touching task, inspect live staging first via the **read-only Supabase MCP** (`mcp__supabase__list_tables`, `execute_sql`, `list_edge_functions`, `get_edge_function`) — never guess schema or deployed state.
4. **PLAN.** Write a 3–6 line plan (files to touch, approach, how Verify will pass) into your working notes before editing. If the plan requires a decision the spec doesn't make, choose the simplest thing that passes Verify and record it in the **Decision Log**.
5. **EXECUTE.** Smallest coherent change. Match surrounding code style exactly (tokens/theme roles only — no raw hexes; reduce-motion + web gating on every animation; typed `track()` facade for analytics; keep `PREVIEW_*` fixtures intact for the `/dev` routes — production routes stop using them, dev routes keep them).
6. **VERIFY.** Run the task's **Verify** line literally, **plus the standing gates** (below) for every task that touches `app/`: from `app/` → `npm run typecheck` (0 errors), `npm run lint` (0 problems), `npm run test:ci` (green). Edge-function tasks additionally: from `supabase/functions` → `deno test --allow-read --allow-env` (Deno lives at `C:\Users\leheh\.deno\bin\deno.exe`). Only if everything passes:
   - change `[ ]` → `[x]` (or `[~]` if a device-pending leg remains — say exactly which leg in an indented note; **never fake a green**),
   - append one line to the Build Log,
   - update the STATE block,
   - `git add -A && git commit -m "F#.T# <short description>"`.
7. **On failure:** retry up to 3 *distinct* approaches. Still failing → mark `[!]`, record the failure + approaches in an indented note, set STATE `Blocked on`, move to the next `∥` task if one exists, else report and **stop**. A falsely-green ledger is worse than a stalled one.
8. **Session budget.** One task at a time; keep going while context allows. Near the limit: finish or `[~]`-note the in-flight task, update STATE, commit, stop cleanly.

### Standing rules (apply to every task)

- **Never fake a green.** Web screenshots capture static end-states only — live reanimated motion, haptics, camera, native share sheet, RevenueCat purchase, and push delivery are **device-pending**: build them fully, verify what is verifiable device-free, and mark the live leg `[~]` honestly.
- **Screenshot verification method (established):** from `app/`: `npx expo export --platform web`, then `node scripts/shoot.mjs <outDir> <route:WxH[=name]> …` — routes are **CLI arguments** (390×844 standard, 320-wide where clipping matters). The launcher must be requested as the root route (`/`), NOT `/index` — the old harness invocations got this wrong and captured 404s. Dark mode needs a separate export: `EXPO_PUBLIC_FORCE_SCHEME=dark npx expo export --platform web` then shoot again. Save all new screenshots under `docs/checkpoints/audit2/`.
- **Backend interaction cheatsheet:** deploy functions with `npx supabase@latest functions deploy <fn> --project-ref rphtdgoggsldshtdbkaj` (`SUPABASE_ACCESS_TOKEN` from `.env.staging`; the globally installed CLI 2.101.0 cannot parse config.toml — always `npx supabase@latest`). Delete a stale fn with `npx supabase@latest functions delete <fn> --project-ref rphtdgoggsldshtdbkaj`. Per-fn `verify_jwt` is encoded in `supabase/config.toml [functions.*]`. Migrations: **new files only, expand-contract (additive)**, applied with `db push --db-url` from `.env.staging`. **The Supabase MCP is READ-ONLY** — every seed row, SQL UPDATE, or `queue_send` a Verify needs runs through a throwaway Node/pg script using `.env.staging` credentials (pattern: `supabase/tests/`; `node --test --test-concurrency=1` is the suite runner there). **Seed ownership matters:** rows a Verify expects the app to READ must be owned by the app session's user id (RLS) — either create them through the app flow and drive status by SQL, or read the web session's user id first and seed rows owned by it. **Clean up seeded rows after each verify; never commit secrets or seed scripts containing them.**
- **🚫 Do NOT schedule pg_cron jobs or install pg_net.** Cron→worker wiring is a parked, security-sensitive backend task (service key in Vault) outside this ledger. To advance a pipeline row in tests, **invoke the worker function directly** with the service key (established pattern: `worker-narrative` was live-validated this way).
- **Analytics discipline:** every event goes through the typed facade in `app/src/lib/analytics.ts`; when adding an event, update `AnalyticsEventMap` AND `docs/ANALYTICS.md` in the same commit.
- **Copy discipline:** no CJK in default UI; no health/medical claims; the canonical deletion promise (set in F1.T5) is the only deletion wording allowed anywhere.
- **When you wire a surface, emit its events** (the F0.T12 sweep is a backstop, not an excuse to defer).
